# Web software updates, voice sit/stand, and a component package shared with the image

**English** · [简体中文](2026-10-27-web-updates-design.md)

The user has approved the [online upgrade flow proposal](../../online-update-flow-design-20261027.en.md), asking for it to be implemented with local voice sit down/stand up included, and for the new image to use the same install package afterwards. Free-form AI voice remains paused, and its drafts are not merged. The scope is the web console, the matching helper and the duck-echo program of the existing HD1910/Radxa Zero3W replica stack; robotd/padd/models/OS stay at the existing verified versions.

## Verified engine choice

Reuse the base image's real ARM64 updaterd 0.15.1/rev 1fa84386/API37, copied to a stable path owned by a separate root, and not updated inside the ordinary software package. On 2026-10-27, using the existing qemu-aarch64 and five read-only extracted shared libraries in WSL, the version query, a custom profile --self-test and real IPC were run, confirming that local_dir, the component software, Restart, command health checks, and exact/from_dir/dry_run are usable. No separate signing/transaction/rollback engine was written.

The component `software` is a single transaction: `/opt/microduck/software/releases/<semver>/{studio,duck-echo}` plus an atomic current link; the helper ships with the Studio version and uses a stable root wrapper entry. The stable systemd units, the updater, health checks, the release public key and user data are outside this directory. Configuration is auto_apply=off, with no periodic checks. Only microduck-studio and duck-echo are restarted. robotd/padd are neither updated nor restarted.

ASR dependencies/models live in `/opt/microduck/resources/{asr-deps,models}` and are passed to the voice service via explicit parameters; the default is actions+toggle+duck, and it does not start listening automatically at startup. Mic3R initialization is a stable startup preparation step, keeping the original sound card initialization without touching the speaker volume. The R3 toggle cue sounds and the accepted sit/stand semantics are kept.

## Package, signing, checks and download

The whole-set version is preferably `2026.10.27` (later same-day revisions use a SemVer-permitted format), with the independent source SHA/file hashes registered. The maintainer's own minisign release public key is used; the private key lives only in a private signing directory on the local machine and must not go into Git/install packages/images. The first package is built from a runtime whitelist of frozen Git, containing no development state, Keys or logs.

The online source is fixed to the official `microduck-software-v*` releases of the user's repo fanhao375/microduck-replica; an image release must not be mistaken for a component release. With no matching release it shows "尚无发布的软件更新" (No software updates have been released yet), and a network failure does not show up-to-date. The built-in source/trust configuration is root-managed, and the web page does not offer arbitrary root commands, install paths or release source overrides.

The distribution outer package contains only four plain files for one version: `<version>.manifest.json` and its signature, the component archive and its signature. manifest.channel=software, url is a bare local file name, and hash/size/version/source/compatibility information is fixed; the same outer package can be both downloaded over HTTPS and uploaded through the web page. The outer package strictly limits count/total size/file names, rejects absolute paths, .., links, duplicate members and special files, and unverified code is not executed.

The existing engine has no download verb, and the check result does not return an artifact URL. A small restricted control service does the release metadata lookup, size-limited download/outer-package caching and task records, with the cache root-private; it hands off to the real engine's exact/from_dir/dry_run to complete signature, hash, compatibility, archive and required-files verification, and only then shows it as installable. Actual installation calls the same exact/from_dir again, reusing the same cache and re-verifying. All displayed metadata is untrusted plain text. If dry_run's motion precheck is not yet satisfied, it shows downloaded but pending parked verification, and must not show a false green.

The control service is independent of Studio, and install/rollback tasks do not depend on a web request staying alive; task ID, stage/error/result are written to the update state directory and can be read back after a page refresh or Studio restart. Download, verification, preparation, apply, health check, completion and rollback/failure are shown separately; there is limited concurrency and a single install lock. The source/catalog URL and upload/download limits are fixed, and HTTP is only allowed for explicit loopback tests; public network uses TLS verification and a limited number of controlled redirects, and credentials are never carried to unfamiliar targets.

## Install preconditions and recovery

Before dry_run/apply/rollback, the control layer reads the real robot.busStatus and requires motion/control/homed, policy_enabled=false, fresh joint feedback/no actual motion, and checks that Studio servo/calibration/recording-playback sessions and voice listening/music are off. Missing readback means refusal; the replica stack's install protections must not be skipped just because the upstream engine allows robotd to be absent. Stable power/low battery and free disk space are checked, and errors state the specific reason. During installation, new motion/configuration operations are rejected, and the update hold is released after reconnecting; disabling buttons cannot serve as the server-side lock.

The stable health command verifies the current manifest, the source of the actually running programs, Studio healthz + static assets, the duck-echo control socket, the required ASR resources, and that robotd/padd were not restarted; a service that is missing or active but not ready cannot count as success. On check failure, the original engine restores the previous version link and starts the old services. There is no destructive external migration hook; the first new image plants a valid baseline, and every later upgrade keeps the previous version. User calibration/Wi-Fi/pairing/recordings/API Key are all outside the version directory, and overwriting them with the publisher's state is forbidden. Power loss/executor crash recovery is accepted according to the original engine's persistent transactions, without exaggerating physical power-loss tests that were not done.

A one-time bootstrap keeps the old installation/units and data, installs the stable component configuration and entry, and uses the same signed package/original engine initial install; on verification failure it restores the old service configuration. The new image installs the same signed package through the same installer's offline rootfs entry, allowing an explicit QEMU command for the build, and ARM code is not executed on the x86 host. Ordinary upgrades do not change the OS/kernel, runtime or personal network.

## Web console and permissions

"软件更新" (Software update) at the top of the settings page: current suite/component versions, release notes, check for updates, download/upload package, version pending install, update now, roll back to the previous version, and real progress/results. It uses the existing visual style and 320px layout. All HTTP reuses the web login, Host/Origin/CSRF, requires a password to be set (except the explicit localhost development mode), no-store, input whitelists and size limits. Backend file and network work does not block the main event loop.

When installation starts, it shows that the web page may briefly disconnect, reconnects automatically and determines success from the task record; locally cached packages can be installed/rolled back offline. Without a real release source, a fake latest version cannot be demonstrated; a real local HTTPS/loopback provider tests the download path, and the actual engine tests signing/installation/rollback in a temporary root in WSL.

## Acceptance check and delivery

Failing tests come first; the actual old ARM engine + a locally signed package pass first install, switching to the new version, automatic recovery from bad signature/wrong hash/out-of-bounds package/service failure, and task crash recovery. Real local Edge verifies login/CSRF, no release, check/download/upload/install/reconnect/rollback/errors/narrow screen; mocking a single success return is not enough. The original voice-related tests match the runtime files/resources, and the accepted recognition logic is not rewritten. On the robot: frozen manifest, backup, real parked check, and user data hash/robotd/padd identity verification. New image build, read-only check after extraction, firmware and model hashes/clean identity/no private key and API Key check; first installation of a new card by a real person and this image's acoustics still need actual acceptance, and success with the old version cannot substitute for it.
