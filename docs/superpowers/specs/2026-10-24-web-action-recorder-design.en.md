## Scope the user has already decided

- Start recording by clicking in the web page, operating with the existing web remote and virtual joystick, without relying on physical gamepad button mappings.
- Include forward, backward and turning; record the speed, direction and duration corresponding to the web operations, then play them back on the timeline.
- Recording can be stopped and saved with a name, after which a recording can be selected for repeated playback.
- Sound recording, sound-triggered actions and sound imitation are a later separate phase and are not implemented this time.

## Approach selection

Recommended: record the web control commands that pass the existing permission and state checks and are actually allowed to be sent, plus relative time. Playback also goes through the same checks and keeps the approach where the main program is responsible for balance and joint control.

The alternative is to capture all joint angles and replay the joint trajectories directly. It suits a separate future study of hand-guided teaching, but it needs to handle standing balance, ground contact and joint torque, and cannot serve as a substitute implementation for this round's web command recording.

This feature repeats control commands and rhythm; it does not guarantee the same steps, foot placement or spatial path. The starting posture, the floor and slipping all change the actual motion; the wording "return the same way" or "exact trajectory playback" is not used.

## Web usage flow

Add a "动作录制" (Action recording) area inside the existing remote card, near the stand, walk and sit buttons; no new physical gamepad binding is added.

1. The user gets the duck standing steadily through the usual flow. The record button itself does not trigger standing up, enabling torque or starting to walk.
2. Click "开始录制" (Start recording); a red recording state, the elapsed recording time and "暂停录制／结束录制" (Pause recording / Finish recording) are shown.
3. Operate the existing web joystick, head / body modes, mouth opening, sounds and supported actions. Calibration, settings changes and model changes in the UI are not part of the action recording.
4. Clicking "暂停录制" (Pause recording) stops continuous motion and recenters; the paused waiting time does not go into the final clip; after resuming, recording starts from new operations and does not continue a joystick held before the pause.
5. Click "结束录制" (Finish recording), stop continuous motion, enter a name and save. When there are no valid actions, the reason is explained and no empty recording is created.
6. Select a recording from the list, view its name, duration and required model / features, and choose to play it 1, 3 or 5 times, defaulting to 1.
7. Explicitly click "开始回放" (Start playback). Progress, the current step, remaining repetitions and "暂停回放／停止回放" (Pause playback / Stop playback) are shown, and the e-stop at the top remains available.

Recordings can be renamed and deleted. The first version has no editing, splicing, speed changes, file import or infinite loops.

## Recording content and starting conditions

- Record the web control events accepted by the server along with monotonic clock time; do not capture raw browser keyboard events, and do not treat all JSON-RPC as replayable content.
- The continuous channel records the clamped speed / angular velocity, head, body and mouth intents, and stop boundaries. Mode changes are saved explicitly, without relying on the page's joystick mode before playback.
- Actions and skills record known action identifiers and lifecycle; sounds record known sound identifiers. Arbitrary method names, file paths or programs must not be written into a recording.
- Stand up, start walking and sit down are state preparations the user completes manually before recording; the first version does not treat these transitions as playback steps. If these preparation states change during operation, or torque is turned off, calibration is entered or the model is changed, the current recording / playback ends and the reason is shown.
- If the content requires the walking policy, both recording and playback require the duck to already be in the "准备好走" (ready to walk) state. Real-time state, the current model and speed limits are checked; the old state in the recording file is not used in place of the check.
- When a physical gamepad is connected, the existing web remote mutual-exclusion rules apply; if the web joystick is unavailable, this web recording cannot start, and the reason is explained.
- Save the necessary model / configuration fingerprints. When the relevant model or control configuration does not match, playback is refused with a prompt to re-record, so that the same identifier does not turn into a different action.

## Pause, stop and execution boundaries

- Pausing playback stops walking, clears sustained head / body / mouth control, and issues no further steps; the timeline stays at the current position. Resuming requires an explicit click from the user and re-checks the state.
- Already triggered skills such as kicks and rolls cannot be assumed to have physically stopped just because commands are no longer sent. Whether the runtime supports cancellation must be checked; when it does not, an ordinary pause takes effect when the current skill ends, and the UI shows "等待当前技能结束" (Waiting for the current skill to finish). The e-stop always uses the original torque-off channel.
- "停止回放" (Stop playback) cancels the remaining steps and later loops, and stops continuous control. An e-stop or ordinary stop must not be disguised as continuing in the background.
- Only one recording or playback session exists at a time. Conflicting ordinary controls are disabled during playback; manual takeover first ends playback and then accepts new control.
- Switching pages, scrolling out of the control area, hiding the tab, window losing focus, connection loss, change of control ownership, abnormal state or e-stop all end recording / playback. Restoring the connection does not resume playback automatically.
- The server executes the timeline and requires the current web page to send a valid keep-alive signal every 100 milliseconds. If no signal arrives for more than 500 milliseconds it must stop; the server must not keep sending speed indefinitely and bypass the existing deadman.
- The existing low-voltage, servo fault, IMU state or model readiness checks are not bypassed for playback.
- At the end of each loop, stop continuous motion, exit the body latch and close the mouth; the next loop begins only after re-checking the state. Torque is not re-enabled automatically.

## Data and module boundaries

- Recording, file validation and timeline execution use a separate module; it interacts through PadOps' authorized control entry points, rather than piling the full implementation into the already large web page or pad_drive.py.
- Saved files use a versioned data structure: identifier, name, creation time, effective duration, starting requirements, configuration fingerprint and a whitelisted event list.
- Store them in Studio's state directory without modifying the image's default actions. Files use atomic replacement, with limits on count, duration, name, file size, event count and parameter ranges.
- First-version limits: 60 seconds per recording, at most 20 recordings, at most 5 repetitions. Names are at most 32 characters, a single file at most 1 MiB and 6,000 events; non-finite numbers, out-of-order times and unknown events are rejected. Reaching the duration or event limit automatically ends the recording as a draft pending save; a failed save does not show success.
- No camera video or microphone audio is recorded. This feature and the camera preview can be used at the same time, but each manages its own resources.
- Data is stored on the board; the web page is not a robot task scheduler that runs independently in the background. Unsaved drafts are not guaranteed to survive a service restart, and the UI clearly shows "尚未保存" (Not yet saved).

## Verification and delivery

Pure logic tests cover time ordering, removal of paused waiting time, rebuilding the continuous channel, recentering at the end of a loop, rejection of corrupted files / out-of-range parameters, configuration mismatch and mutual exclusion of concurrent sessions.

Use a fake robotd to check the intents actually sent and their order, and verify that disconnection, late events, takeover, e-stop, background and refresh do not resume playback. Playback success cannot be judged only from a button changing color.

Browser checks cover the record, save, name, play, pause, stop, finite loop and delete flows on desktop and 320 / 390px narrow screens, and that the recording bar does not affect the existing remote and camera layout.

Complete local simulation and regression first. Acceptance on the real duck is done separately, starting with short, low-speed clips, recording motion deviation and the real behavior of skill cancellation; passing locally does not mean board-side verification is done. The image is not automatically re-flashed or deployed.

## Later voice interaction roadmap

The existing project has sound card initialization, onboard microphone input routing and the basics of sound playback; Studio does not yet have user recording, sound learning or sound-triggered actions, and real microphone capture has not yet been verified in this task.

First do manual recording and listen-back to confirm the onboard microphone and speaker chain; then do "parrot mode" (repeat after me): record a sentence, play back the original or a voice-changed version, with mouth motion. After that, study binding a specific command phrase or sound to a saved action, adding rejection of unknown sounds, trigger intervals and speaker echo suppression, and measure false triggers in practice amid servo noise.

"Replaying the words just heard" and "cloning the voice to generate new speech" are different features; a demo of the former cannot be claimed as the latter. Sound recognition only produces action requests and must still go through the same readiness and stop checks; hearing a sound does not bypass control ownership to start walking directly.

Technical references for the voice phase: [ALSA official recording and playback test](https://wiki.alsa-project.org/wiki/SoundcardTesting), [TensorFlow official keyword recognition example](https://www.tensorflow.org/tutorials/audio/simple_audio). These only support feasibility research and do not prove that the current duck has completed capture or recognition.
