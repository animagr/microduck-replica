## How actions will be organized going forward

We recommend extending a list of callable actions on top of the existing model library and combo actions, each with a stable identifier, name, type, applicable state, termination mode and required model. The user chooses "what this button does" in the web console and can also set a voice command for the same action. The underlying execution methods are handled separately; the page should not require users to understand file paths.

| Type | Example | Relation to what exists now |
| --- | --- | --- |
| Model skill | Pick up with the new pick-up model, or bind a newly registered skill | Model import/selection and the five skill buttons exist; the model must match the execution contract, and a continuous walking model is not the same as a one-shot skill. |
| Program feature or combo | Voice-changer repeat toggle, nod plus quack, greeting | The web console combos and the standalone voice service have part of the capability; unified binding is not implemented yet. |
| Saved replay | Record a sequence of operations, name it "Showcase 1", trigger it with a button | Web console recording, naming and replay are implemented; physical gamepad / voice binding is a later extension, not in the first version. |

The existing "swap the pick-up model" and "change button A to another action" are two different operations and should be shown separately; restoring default button mappings should not delete models or recordings. Conflict handling for basic controls such as Start and Select and for R3 recording needs to be made explicit; "every button can be remapped" must not be presented as a current capability.

Replay has already been implemented following the Oct 24 design: start recording in the web console → operate → stop and name → select a recording → play 1/3/5 times. It records the intents that were allowed to be sent and their relative timing, while the original main program remains responsible for joints and balance; after relevant model or control configuration changes, replaying old recordings is refused. Joint teaching and exact spatial trajectories are a separate future research topic. Model skills lack reliable completion readback and are rejected outright during recording; regular manual skills keep their original behavior.

## Image and online upgrade: recommend a shared versioned package

All three delivery methods need to be kept, but they serve different purposes:

| Method | Purpose | Current status |
| --- | --- | --- |
| SSH installation | Development, troubleshooting, quick verification on one duck | Available now, but changes must go into the source code, versioned package and acceptance records. |
| Component versioned package + web console online upgrade | Adding features and fixing software on ducks that already have the system installed | The 2026.10.27 signed package and web console flow are done locally; the current robot still needs a one-time SSH bootstrap and a physical acceptance check. |
| Baseline system image | First installation on a new card, system recovery, necessary low-level migrations | The new 20261027 local image consumes the same signed package and passed an extract-and-read-only acceptance check; not yet on the robot or published. |

The new image and online upgrade should use **the same frozen version manifest and installation logic**. An image is a snapshot of a given version's software package installed on a clean system; ducks already in use install the same versioned package and keep their own data. A public release is not made by copying all state directly from a personal SD card under development.

We recommend splitting components by dependency: system base (bootloader/kernel/device tree), the compatible Feetech runtime, Studio and the matching helper, the voice service and recognition resources, and motion models. When Studio/helper have interface dependencies, they are updated as a group; an official update that does not match the runtime must not overwrite the Feetech/IMU extensions. The PC training studio is released separately and not installed into the duck's low-compute system. The IMU daughterboard firmware has its own hardware upgrade process; we do not promise that a regular Linux software package can replace flashing it.

The install package should describe at least: version, source commit, CPU/OS/hardware requirements, component dependencies and interface versions, file hashes, configuration schema version, migration/rollback method, which services need restarting and whether a system reboot is required. There should be a trusted release source and package verification; first download and verify, check the actual state, keep the old version, then install, check services and configuration readback, and record the version only after confirming success. On failure, "downloaded" or "service start command succeeded" must not be displayed as "upgrade succeeded".

The original project's updater design: [updater-design.md](../../Microduck-kissqy/microduck-hd1910/firmware/docs/design/updater-design.md). On Oct 27 the actual ARM engine was verified, with a separate software configuration and our own release public key; this round only completed the local components / image and did not enable the old update service on the current robot. The Feetech runtime and system are still handled under separate contracts.

The web console can offer "current version → check for updates → update contents/impact → user clicks upgrade → progress and result → roll back to the previous version when available". Download and actual switchover are separate; switchover requires the duck to be in a permitted state, and the runtime must not be replaced in the background while it is walking. Core service updates usually briefly stop the corresponding control; zero-downtime hot upgrade is not advertised.

### User data that must be preserved

The upgrade design needs to cover, item by item: servo zero position / direction / limits and tuned parameters, IMU mounting orientation and session recovery data, the user's Wi-Fi / gamepad pairing, login and SSH settings, imported models, current selection / button mappings, the duck profile, saved actions and voice preferences. Configuration migration must verify that the old version can read it back; where backward compatibility is impossible, the rollback boundary must be stated explicitly.

A public image, on the other hand, must have personal Wi-Fi passwords, SSH keys, host identity, login sessions, pairings and recordings cleared. The home SSID in F18 is only this duck's setting and must not become a public default.
