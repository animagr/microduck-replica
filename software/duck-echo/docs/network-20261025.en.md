# 2026-10-25 network recovery and gamepad retest

**English** · [简体中文](network-20261025.md)

The target is duck-0de6 at 192.168.0.102, a Radxa Zero3W. This time the network configuration was changed over SSH, with no reflashing needed. robotd, padd, bluetooth and the whole robot were not restarted during this work.

## Network configuration and boundaries

The previously saved TP-LINK_6494 (2.4 GHz) repeatedly failed to associate in this boot's logs, with NetworkManager reporting ssid-not-found; the device then fell back to hotspot mode. After connecting to TP-LINK_5G_6494 via the device's existing Bluetooth network setup interface, SSH and the web console were restored.

This duck's 5 GHz profile UUID is 2f1b4328-749a-4e69-b37c-e7d96e255378, with the following settings saved:

| Setting | Actual value |
| --- | --- |
| Auto-connect | yes |
| Auto-connect priority | 200 |
| Allowed band | a (5 GHz) |
| Wi-Fi power saving | disable (2) |
| Auto-connect for the other two saved STA networks | no |
| Last actual connection | TP-LINK_5G_6494, 5240 MHz |

The old network profiles are kept, and the hotspot fallback feature is kept. After shutting down an idle hotspot, microduck-netcheck hands reconnection over to NetworkManager's auto-connect and does not force-start the disabled profiles one by one. The device will not currently switch automatically to the disabled 2.4 GHz profile.

This is a fixed setting for this particular device; the generic network-selection logic of the network setup page was not changed. If the user manually selects another network later, the allowed band and auto-connect settings need to be adjusted accordingly. If the same SSID offers both bands, use band=a for 5 GHz and band=bg for 2.4 GHz.

The original settings are backed up on the device at /var/lib/duck-network-20261025/profiles-before.json, a directory restricted to root. The configuration script fix_5g.py restores the previous settings if this write fails. Neither the backup nor the diagnostic summary contains the Wi-Fi password. The Wi-Fi and Bluetooth temporarily enabled on the computer have been returned to their pre-operation disconnected and off states.

## Real-hardware verification

The original URL http://duck-0de6:8000/#/pad works again, and the user explicitly confirmed "网页好了" (the web page works now). The retest accessed /healthz 20 times, alternating between the hostname and the IP, and all returned HTTP 200; IP requests took 0–31 ms. Some hostname requests took about 2.7 seconds, including name resolution time, with no timeouts. The computer's hosts file, VPN and router configuration were not changed.

To separate the voice service from gamepad problems, only the standalone duck-echo service was stopped and restored, and HCI data was passively recorded for each case. The raw recordings stay in a restricted directory on the device; no HID data or link keys were exported, and statistical summaries are saved locally.

| --- | ---: | ---: | ---: | ---: | ---: |
| Off | 160.103 s | 11168 | 48.743 ms | 0 | 0 |
| On | 180.141 s | 12548 | 48.722 ms | 0 | 0 |

Both recordings are complete, with no active disconnect commands and no gamepad receive gap over 100 ms. The user reported still seeing the light blink after turning voice off, then explicitly stated "只看到灯闪，动作正常" (I only saw the light blink, the actions were normal), consistent with the recording showing no disconnect in that window.

During the voice-on window, the user used R3 to complete two echoes of ordinary speech and then gave commands. The device's local log shows sit down at 13:35:32 and stand up at 13:35:35, both returning accepted=true, changed=true. The user confirmed "能复读，摇杆也正常" (echo works, and the sticks are fine too). Timestamps use the device clock, which is offset from the computer's time, so they are not treated as the computer's local time.

At the end, duck-echo was active and enabled, in actions mode. robotd PID 1117, padd PID 1147 and bluetooth PID 695 stayed unchanged, and none restarted automatically. The temporary passive recording service has been stopped.

## Conclusions that cannot be drawn yet

The old logs from this boot do show pad gone followed by reconnection at 13:10 and 13:27, the latter lasting about 9 seconds. These events happened before passive recording started, so there is no corresponding HCI disconnect reason. A short period of normal behavior afterwards is not enough to conclude that the earlier real drops are fixed for good, nor can they be attributed directly to voice. The blinking light the user currently reports is not accompanied by interrupted actions.
